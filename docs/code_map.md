## Files

### multiplexer: The multiplexer and both client libraries

- [BUILD](../multiplexer/BUILD): The multiplexer, the C++ client library and the Python package, with the generated constants and protocol buffer code they share.
- [Multiplexer.proto](../multiplexer/Multiplexer.proto): The protocol's messages: MultiplexerMessage is the envelope every frame carries; WelcomeMessage, BackendForPacketSearch and DeliveryError are the payloads of the protocol's own message types; MultiplexerRules with its peer and message descriptions is the schema of the rules file. docs/wire_format.md and docs/rules.md describe them from the outside.
- [Recording.proto](../multiplexer/Recording.proto): What a multiplexer records: a stream of Record messages, varint-length- prefixed (lib/protobuf/stream.h), one per event. The first is a RecordingHeader; then a PeerEvent for every peer that registers or leaves, and a RoutedMessage for every delivery attempt at the routing point, one per recipient. A recording is written to a file (--record at start, or a session started over the protocol) or streamed to a peer that tapped in; RecordingControl and RecordingStatus are the messages of that protocol. docs/operations.md describes it from the outside; multiplexer/recording.py reads and drives it.
- [_native.cc](../multiplexer/_native.cc): The Python extension module multiplexer._native: pybind11 bindings for Client (as multiplexer.mxclient.Client's base), its exceptions and trackers, the io_service, the logging entry points, and the constants from defaults.h. mxclient.py wraps this into the Python API; nothing else imports _native directly.
- [basic_client.cc](../multiplexer/basic_client.cc): BasicClient: the parts that are not templates or one-liners. See basic_client.h for the design.
- [basic_client.h](../multiplexer/basic_client.h): The client side of the protocol: connections to one or more multiplexers, an incoming queue, and reconnection. Used by Client (client.h), which adds the query algorithm and the calls peers actually make; nothing else includes this directly.
- [client.cc](../multiplexer/client.cc): Client: constructors, and the query algorithm with the send-and-receive it is built on. The design is in client.h.
- [client.h](../multiplexer/client.h): The C++ client API: connect to multiplexers, send events, ask requests, receive messages. This is what peers use directly and what the Python binding (_native.cc) wraps; BaseMultiplexerServer builds backends on it. docs/api_cpp.md describes it from the caller's side.
- [clients.py](../multiplexer/clients.py): The Python client API: Client, and MxClient to hold one.
- [config.h](../multiplexer/config.h): The rules file in memory: peer types by number and by name, message types by number with their routing rules resolved to peer type numbers.
- [connections_manager.cc](../multiplexer/connections_manager.cc): The CONNECTION_WELCOME frame a manager sends after connecting: a WelcomeMessage with its peer type and instance id, serialized once and reused for every connection.
- [connections_manager.h](../multiplexer/connections_manager.h): What the multiplexer and the client library have in common: first set of Connections indexed by peer id and by peer type, registration on the welcome handshake, the rules file (Config), and the instance id.
- [defaults.h](../multiplexer/defaults.h): Every timeout and limit, compiled into the multiplexer and both client libraries (the Python binding exports them as module attributes). docs/guarantees.md has the same table with context. Changing one means rebuilding everything that embeds it, and the heartbeat intervals must agree between a multiplexer and its peers.
- [fork_test.cc](../multiplexer/fork_test.cc): Clients inherited across fork() are orphans in the child: every call throws UsedAfterFork, destroying them neither hangs nor touches the parent's connections, and the parent's clients keep working. See lib/fork.h.
- [fork_test.py](../multiplexer/fork_test.py): Clients inherited across fork() are orphans in the child.
- [generate_constants.cc](../multiplexer/generate_constants.cc): Build-time tool: reads a rules file and writes the constants for one language, multiplexer.constants.h (namespaces multiplexer::types and multiplexer::peers) or multiplexer_constants.py (classes types and peers), chosen by the output file's extension. Both include a get_name() that maps a number back to its name, for logs. Run by the genrules in multiplexer/BUILD on the file selected by //:multiplexer_rules.
- [in_process_multiplexer.h](../multiplexer/in_process_multiplexer.h): InProcessMultiplexer: a multiplexer on a free port, driven by a thread of its own, for unit tests that need a real one without the integration harness. Uses the repository's multiplexer.rules.
- [interpreter_exit_test.py](../multiplexer/interpreter_exit_test.py): Daemon threads blocked in native waits when the interpreter exits.
- [leak_test.py](../multiplexer/leak_test.py): Leak tests for the Python side of the library and the binding.
- [mxclient.py](../multiplexer/mxclient.py): The Python Client: a thin layer over the C++ Client in multiplexer._native.
- [mxlog_test.py](../multiplexer/mxlog_test.py): Unit tests for multiplexer.mxlog: entries with data must not fail.
- [no_connection_test.py](../multiplexer/no_connection_test.py): A Client with no connections must time out, call after call, never spin.
- [pickle_test.py](../multiplexer/pickle_test.py): The pickle convention end to end: query_pickle, blocking and with a callback, send_pickle and a MultiplexerServer, over a real multiplexer.
- [protocolbuffers.py](../multiplexer/protocolbuffers.py): Adds MultiplexerMessage.from_ as an alias of the `from` field, which is a Python keyword and otherwise reachable only through getattr(). Imported for its side effect by mxclient.
- [recorder.cc](../multiplexer/recorder.cc): See recorder.h.
- [recorder.h](../multiplexer/recorder.h): Recording: the Record messages (Recording.proto) a multiplexer produces, and the Recorder that writes them to a file, through a buffered stream on the io thread, so routing never waits on the disk. A write error switches the file off and is logged once; the multiplexer keeps serving. The server (server.h) owns one Recorder per file session and streams the same records to the peers that tapped in.
- [recorder_test.cc](../multiplexer/recorder_test.cc): The session label rules and the session file name, the parts of remote recording that keep a request from choosing a path.
- [recording.py](../multiplexer/recording.py): A multiplexer's recording: reading it, and starting, stopping or tapping it over the protocol.

- [serve_thread_test.py](../multiplexer/serve_thread_test.py): A backend built on one thread and served from another.
- [server.cc](../multiplexer/server.cc): Server: construction, accepting, and the routing path. The design is in server.h; this file is the whole per-message path, kept in one translation unit so it inlines the way it did as header code.
- [server.h](../multiplexer/server.h): The multiplexer itself: accepts connections and routes every message it receives according to the rules file, to one peer, to all peers of a type, or to the instance id named in the message.
- [servers.py](../multiplexer/servers.py): The Python backend API: BaseMultiplexerServer, which a backend subclasses.
- [soak_test.cc](../multiplexer/soak_test.cc): An in-process soak: a Server, a backend on a thread of its own and a ThreadedClient, thousands of queries, and the C heap measured exactly before and after. A leak per message in the core shows here in about a second, without the integration harness.
- [threaded_client.cc](../multiplexer/threaded_client.cc): ThreadedClient: the io thread, the cross-thread calls, and the query state machine. See the header for the design.
- [threaded_client.h](../multiplexer/threaded_client.h): A client with a thread of its own: the connections live on an io thread that runs all the time, so heartbeats flow and reconnects happen whether or not the program is calling in. Any thread may send and query.
- [threaded_client.py](../multiplexer/threaded_client.py): ThreadedClient: a client with an io thread of its own.
- [threaded_client_py_test.py](../multiplexer/threaded_client_py_test.py): ThreadedClient from Python: on_message, pings, and the io-thread rule.

- [log_tokens.h](../lib/logging/log_tokens.h): The meaning of each MX_LOG / MX_ENTER token (TEXT, FLOW, DATA, CTX, CONTEXT, LEVEL, VERBOSITY, MUSTLOG, SKIPFILEIF) at each stage of the macro expansion: before the should_log check, after it, and just before emitting. Adding a token means adding it to lib/preproc/kwargs.h and to every stage here.
- [logging.cc](../lib/logging/logging.cc): Logging runtime: the verbosity table, the stderr text form, the optional binary stream (length-prefixed LogEntry records via lib/protobuf/stream.h), and the process context (hostname.program[.suffix]).
- [logging.h](../lib/logging/logging.h): Structured logging: MX_LOG(level, verbosity, tokens...) and MX_ENTER / MX_LEAVE. Each entry is a LogEntry protocol buffer (Logging.proto), written as text to stderr and, when set_logging_fd/file was called, as a binary stream that mxcontrol streamlogs can forward. The Python library logs through the same functions via the _native binding, so both languages share one stream and one filter.

### lib/preproc: Preprocessor helpers

- [BUILD](../lib/preproc/BUILD): Preprocessor helper headers.
- [common.h](../lib/preproc/common.h): Small preprocessor helpers shared by the macro-heavy headers: unique names, parenthesis removal, always_inline.
- [create_message.h](../lib/preproc/create_message.h): MX_CREATE_MESSAGE(Type, name, (set_a(1))(set_b(2))): declare a protocol buffer message and call setters on it, in one expression-like line. Used by the logging DATA() token and by the client for protocol messages.
- [create_message_detail.h](../lib/preproc/create_message_detail.h): Helper macro for lib/preproc/create_message.h.
- [kwargs.h](../lib/preproc/kwargs.h): Keyword-argument tokens for macros: MX_PP_KWARGS_PROCESS(ns, data, TEXT(a) FLOW(b) ...) expands to ns##TEXT(a, data) ns##FLOW(b, data) ... The trick is that each token macro expands to the start of a call whose closing parenthesis comes from the next token, with SENTINEL__ closing the last one. Used by the logging macros; see lib/logging/log_tokens.h for the ns## side.

### lib/encoding: Byte encoders

- [BUILD](../lib/encoding/BUILD): Byte encoders for the frame header.
- [base_decoder.h](../lib/encoding/base_decoder.h): BaseDecoder: CRTP base that dispatches decoder(t) to Encoding<T>::decode. See little_endian.h for the one encoding in use.
- [base_encoder.h](../lib/encoding/base_encoder.h): BaseEncoder: CRTP base that dispatches encoder(t) to Encoding<T>::encode.
- [decode_from_range.h](../lib/encoding/decode_from_range.h): DecodeFromRange: a decoder reading bytes from an iterator range; running past the end is an assertion, so callers size the range first.
- [encode_to_range.h](../lib/encoding/encode_to_range.h): EncodeToRange: an encoder writing bytes into an iterator range.
- [little_endian.h](../lib/encoding/little_endian.h): Little-endian uint32, the encoding of the frame header (length, CRC) on the wire; see multiplexer/io/raw_message.h.

### lib/protobuf: Protocol buffer streams

- [BUILD](../lib/protobuf/BUILD): Length-delimited protocol buffer streams, the format of the log files mxcontrol writes and reads; public so that other programs can read them.
- [stream.h](../lib/protobuf/stream.h): Length-delimited protocol buffer streams over std::ostream or a file descriptor. Used by the logging library for its binary stream and by the mxcontrol log commands.
